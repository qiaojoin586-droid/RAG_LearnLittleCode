## 一、P0：必须先修（阻塞 M0 或让文档不可执行）

### P0-1. DDL 第一条建表就失败：`last_value` 是 MySQL 8.0 保留字

附件 B:14 `last_value BIGINT UNSIGNED NOT NULL DEFAULT 0`。`LAST_VALUE` 自 MySQL 8.0.2 起为保留字（官方关键词表标记 R，见 [MySQL 8.0 Keywords and Reserved Words](https://dev.mysql.com/doc/mysqld-version-reference/en/keywords-8-0.html)），未加反引号作为列名会报 `ER_PARSE_ERROR 1064`。整份 DDL 在第一条 `CREATE TABLE ai_version_counters` 即失败。

修复：改列名（建议 `last_num` 或 `next_revision`），并在隔离 MySQL 8 加"整份脚本执行"门禁。这是本轮审查唯一能一眼证伪的硬错误，务必先改。

### P0-2. 新表未写 COLLATE，与现有库排序规则不一致，会导致跨表查询与外键失败

- 附件 B 全部 `CREATE TABLE` 只写 `DEFAULT CHARSET=utf8mb4`、未写 `COLLATE`（B:16、29、40、59、80、124、146、169、189、216、239、268、280、303、323、345、394）。MySQL 8 规则：指定字符集但不指定排序规则时使用**字符集默认排序规则** `utf8mb4_0900_ai_ci`。
- 而现库由 `docker-compose.yml:38` 以 `--collation-server=utf8mb4_unicode_ci` 初始化，`alembic/versions/` 下全部迁移**未指定 charset/collate**（已 grep 确认），既有 `users`/`model_traces`/`tool_call_audit` 为 `utf8mb4_unicode_ci`。
- 后果：新表 `actor_id/subject_user_id/created_by` 与 `users.uuid` JOIN 报 `ERROR 1267 Illegal mix of collations`；B:348-371 在旧表上新增的列继承旧表排序规则，与 `ai_config_releases.id` 比较同样报错；将来给 `users` 加外键会因排序规则不兼容报 `errno 3780`。

修复：全部新表显式 `COLLATE=utf8mb4_unicode_ci`（与现状一致），迁移前用 `information_schema` 核对目标库实际排序规则；旧表若实测为 0900，则统一反向处理。**此项取决于目标库实际配置，落 Alembic 前必须实测确认。**

### P0-3. 错误信封与错误码体系不兼容，M0 就要返工

- 附件 C:7 声称"沿用 code/message/data/request_id"，但现有 `failed_response()` 返回 `{code, message, detail, request_id}`，**没有 `data`**；而 C7:133-148 的错误示例使用 `data.reason`。两者只能有一个成立。
- C7:131 把 `40101` 列为待用段，但该码**已是 `TOKEN_EXPIRED`**（`app/core/failed_response.py:37`）；现有参数校验统一返回 HTTP 422 + 业务码 `40002`，与新增 422xx 段并存且无映射。
- 现有 429 由 `rate_limit.py:172-179` 抛 `HTTPException(detail={...})`，返回体是 FastAPI 的 `{"detail":{...}}`，不符合统一信封，也没有 `request_id`。

修复：在 M0 先定横切契约——`failed_response` 增加 `data`（保留 `detail` 兼容）、建立 code→HTTP 映射表、`40101` 不复用（reauth 用 40110/40111）、`rate_limit` 改抛 `BusinessError`、明确 422 段与 40002 的兼容窗口。附件 C 应引用该映射表而不是"待核对"。

### P0-4. M0 验收与 DDL 阶段标注矛盾：审计精确匹配列在 M1 才加

- 附件 D:15（M0-07）要求"以 run_id/tool_call_id/step_id 精确匹配并发调用"。
- 但附件 B:3（头部）把 trace/audit 扩展归入 **M1**；B:365 又写"M0/M1 复用工具审计表"，两处自相矛盾。按 B:3 的迁移切分，M0 没有这些列；主方案 §13.1（主:524）又要求 M0 承接。

修复：把 `tool_call_audit` 的 ALTER 明确移入 M0 迁移（`model_traces` 的扩展留 M1），统一 B:3 与 B:365 的措辞，并同步主:560。

### P0-5. 异步动作与请求恢复的数据结构不支持 202/7 天重放/租约恢复

- 附件 C:63、C1:28 要求：慢动作返回 202，页面通过 `GET /requests/{id}` 读结果，7 天内可重放，租约失效时先核对再重试；主:303 要求"不在长事务中等待网络"。
- 但附件 B 的 `ai_config_requests`（B:218-239）只有 `payload_hash`，没有可恢复的动作参数（draft_id、expected_draft_version、expected_head_version、roles）、没有 `lease_owner/attempt_count`，也没有按状态/租约/重放窗口的索引；`ai_config_validations`（B:192-216）没有 `request_id`，无法从验证反查请求；`ai_config_releases` 的请求外键只按 `id`、未带作用域（B:267），跨作用域引用只能靠应用层校验。

进程崩溃或租约过期后，工作线程无法安全恢复该动作（要么丢动作，要么重复发布）。修复：`requests` 增 `action_payload JSON`（明文 Key 只以 HMAC/引用形式进入）、`payload_hash_key_version`、`lease_owner`、`attempt_count` 及 `(status,lease_expires_at)`、`(scope,scope,replay_until)` 索引；`validations` 增 `request_id` 与回查索引；`releases` 的请求外键改复合作用域键。

### P0-6. 候选凭据与草稿态不可变版本没有生命周期字段（安全/合规问题）

- 附件 C:71 允许在草稿中提交 `replace` 生成加密候选凭据；附件 C:103 允许草稿 abandoned/expired。
- 但 `ai_secrets`（B:63-84）无 `status=candidate`、无 `origin_draft_id`、无 `candidate_expires_at/retired_at`；`ai_profile_revisions`（B:85-124）无 `status`（而 `ai_prompt_revisions` 有 status，B:141，本身已不对称）；草稿 payload 只是 JSON，无法反查"某个 draft 创建了哪些修订/凭据"。

草稿放弃/过期后，加密 Key 与 draft-only 版本会永久滞留，且无法按草稿定位清理（JSON 扫描 + RESTRICT 外键会阻止删除）。修复：`ai_secrets` 增候选状态与 `origin_draft_id`；profile/prompt 修订增 `source_draft_id` 或新增 `ai_config_draft_items` 反向引用表；定义"无 release 引用 + 草稿结束 → retired/清理"的作业规则。

## 二、P1：进入 M1 详细设计前必须补齐（约 10 项）

### P1-1. head 冲突后的草稿没有出口（并发发布的必然场景）

`POST /drafts`（C:36）要求 `expected_head_version`，`publish`（C:42）再次要求；他人发布后本草稿 publish 返回 409 `HEAD_VERSION_CONFLICT`，但**没有 rebase/刷新基线接口**，PATCH 也不能更新 `base_release_id/base_head_version`。多管理员并发时只能放弃草稿重编。附件 D M1-04（D:47）只要求"冲突返回 409"，没有恢复路径。

建议：新增 `POST /drafts/{id}/rebase`（If-Match + Idempotency-Key，body `expected_head_version`，返回新 draft_version/etag/base_release_id、失效的 validation_ids 与 `status:"editing"`），并在 C4 补状态迁移。

### P1-2. 缺端点策略读取接口，页面的模型连接主流程做不出来

`ai_profile_revisions.endpoint_policy_revision_id` 是**非空外键**（B:102），但附件 C 只有 `POST /endpoint-policies` 创建与 `POST /{id}/revoke` 撤销（C:55-56），**没有列表/详情读取**。页面无法选择已有策略、无法展示网络规则与影响范围；主方案 §11（主:479）却声称附件 C 已补齐端点策略。

建议：增 `GET /endpoint-policies?cursor&limit&status` 与 `GET /endpoint-policies/{id}`（脱敏 `connection_rules`、`policy_key`、`revision`、`environment`、反向引用）；C2:55 请求体补 `policy_key`、`address_mode`（B:46/51 非空）。

### P1-3. 缺字段级 schema：草稿请求体、PATCH 语义、release 清单、credential_state 基数

附件 C:69 声称 ProfileRevision 字段"与 DDL 同名"，但 DDL 是 `connect_timeout_ms/request_timeout_ms/embedding_dimension`（B:108-110），C 写 `timeouts/dimensions`；`credential_state`（C:73-86）定义为**单个对象**，而页面有 16 个角色/多条凭据，到底是哪一条未定义；`POST/PATCH /drafts` 的请求体、草稿 payload、release 清单均无 schema；PATCH 是整体替换还是局部合并、显式 null 语义均未写；`ROLE_BINDING` 的 `failure_mode` 允许值散落在 A:68 与例子里，未成枚举。

建议：补 C3.1 草稿 payload、C3.2 PATCH 请求体（整体替换 + null 清除）、C3.3 release 清单、C3.4 `credentials: [{role_key, ...}]` 数组、`failure_mode` 枚举表；字段名与 DDL 对齐或给映射。

### P1-4. 草稿可发现性：无 `GET /drafts` 列表、无"当前草稿"字段

页面刷新/换设备后 `GET /`（C:34）只返回 head/roles/index_states/permissions，**不能找回编辑中的草稿**；`ai_config_drafts` 也无"每 scope 一个编辑中草稿"的唯一约束或接口约定（B:174-189）。

建议：`GET /` 返回当前草稿摘要，或增 `GET /drafts?status&cursor`；明确同一 scope 是否允许多个并行草稿。

### P1-5. 验证绑定字段与 DDL 不一致

附件 A:85 要求验证绑定 `endpoint_policy_revision` 与 `safety_policy_version`；附件 B:192-216 没有这两列，只有不透明 `target_hash`，且三处均未定义 `target_hash` 的规范化输入与算法版本（主:309 只列"模型、提示词、凭据及适配器版本"）。同一 draft 的验证过期/失效原因不可解释。

建议：二选一——补列，或在 A3/主 §7.2/B:199 **明确定义 `target_hash` 输入=角色契约+完整模型参数+凭据版本+适配器版本+端点策略版本+安全策略版本+规范化算法版本**。

### P1-6. `role_bindings` 无法区分"原始绑定"与"解析后绑定"

`follow_execution` 要求运行时解析为"本轮附件/思考路由实际选中的模型"（A:66），发布时不可能预解析；但 release 只有单列 `role_bindings JSON`（B:255-257），未定义它是 raw 还是 resolved，运行时语义与审计都无从落地。

建议：增 `role_bindings_raw`、`resolved_static_bindings`、`follow_execution_roles` 三列（或明确"只存 raw，解析后绑定由 `GET /drafts/{id}/resolution` 提供并在 trace 记录实际模型"）。

### P1-7. 首次导入/一次性发布没有合法路径

`ai_config_releases.draft_id`、`request_record_id` 均 NOT NULL（B:250-253），且 `release→request`、`release→draft` 有外键；而主方案 §14.1（主:570-577）的一次性导入是部署命令，不产生 HTTP 请求。契约未定义导入事务中的合成 draft/request 行、幂等键（如 `bootstrap.import`）与审计，实施者只能自行决定或改约束。

建议：明确导入行清单与幂等键，或允许 `origin='import'` + 可空 request，并在 C1 增"受控初始化/导入契约"。

### P1-8. 两处 `role_key` 语义碰撞；最后一个管理员可被撤销

- `ai_config_admin_grants.role_key`（B:23）存的是配置权限角色（config_reader/operator/admin），而 A1 的 `role_key` 是 16 个业务用途；同名不同域，前端/实现极易混用。
- 附件 C 的 grant 撤销（C:59）没有"不允许撤销最后一个 config_admin"的保护，误操作会把系统锁死（bootstrap 只在"无管理员"时允许，恰好可恢复，但不该依赖它）。

建议：grants 改 `config_role_key`（C2:58 同步）；C1 增最后管理员保护与审计。

### P1-9. reauth 契约不完整，且与现有认证/部署形态未对齐

C1:22 只写"最近 10 分钟的重新认证证明、放内存、X-Admin-Reauth"，缺响应字段、TTL、错误码、失败限流、进程重启/多 worker 行为；而 `get_current_user_id`（`app/utils/auth_utils.py:381-455`）**只验 JWT 与黑名单，不查 `users.status`、不查 grant**，C1:9"资源状态和账户有效性每次核验"没有落地依赖；Dockerfile 注释确认当前是单 worker 部署，但 C1 未把"单实例"写成可验收前提。

建议：补 reauth 契约（proof/TTL/错误码/限流/复用现有登录失败计数）；新增 `require_config_permission` 依赖（查 status、grant、授权 head、reauth 时效）；C1 写"M1 部署前提=单应用进程，启动自检 worker 数>1 时拒绝启用配置管理"。

### P1-10. M1 的 Embedding 适配器覆盖缺口：DashScope 原生路径未定义

附件 A:16 明确现网 embedding 来源是 `DashScopeEmbeddings`（非 OpenAI 兼容端点）；A4 只定义了 `OpenAIEmbeddings`（显式 base_url、`check_embedding_ctx_length=false`）与 Ollama 的参数；主 §4.1 的 adapter 枚举只有 `openai_compatible`/`ollama_native`（+扩展）。而 M1 又要求"不改已有向量空间、同空间换 Key 只更新连接"（主:433、M1-13）。

即：M1 要么继续用 `DashScopeEmbeddings`（需要一个 vendor-native Embedding 适配器条目），要么切到 DashScope 兼容 `/v1/embeddings`（需要"同空间"的可信证据，而 A3/G4 明确探测不能证明等价）。这个选择未写，M1-13 无法实现。

建议：在 A1/A4 增加 `dashscope_native` embedding 适配器（M1 沿用原封装，指纹=供应商+模型+维度+参数），把"切换兼容端点"列为 M3 重建候选。

### 其他值得在 M1 前明确的 P1/P2

- **回滚与联网验证耦合**：C2:46 的 restore 会"生成新草稿/验证/发布"，A3 验证默认 24 小时有效；若供应商故障、验证过期，则无法回滚到历史可用版本——这与"可恢复"目标冲突。建议明确"历史 release 回滚可复用历史验证/离线预检"的边界。

- **导入来源清单缺 `config/agent.yaml` 的模型相关项**：§14.1（主:571）只列 env/百炼/Ollama/提示词文件，但 A1 的 `reflection` 依赖 `agent.yaml reflection.critic_model`，M1-10 的上下文预算依赖 `token_budget.model_context_size`（现为 32768）。导入必须读取它们。
- **现有重试叠加**：`factory.py:50` 共享 httpx transport 配置了 `retries=1`，OpenAI SDK/ChatOpenAI 自带默认重试；C6"关闭 SDK 内部隐式重试、最多再试 1 次"需要在 ClientRegistry 统一置 `max_retries=0` 并核对传输层重试，否则实际重试次数翻倍。
- **未知价格成本口径**：`usage_service.py:154` 对未配置价格的模型按 0 计费；M1-14 要求"未知费用显示 null 并告警、旧账单不伪造"，需要迁移现有 usage 汇总逻辑，C 契约没有对应的读接口字段。
- **`ai_version_counters` 与 head 的 `last_release_number` 双来源**、head 首行创建/CAS 语义、计数分配 SQL 未给出；建议按"head 行内分配 release_number + 单条 CAS UPDATE 三列 + 0 行转 409"写死（复审附具体 SQL）。
- **不可变仅靠约定**：B:7 说"不可变版本禁止 UPDATE"，但无 DB 层约束；建议生产账号对不可变表只授 SELECT/INSERT，控制列单独授权。
- **状态字典缺失**：B:7 声称"允许值由附件 C 约束"，但 drafts/validations/requests/outbox/grants/endpoint/secret/index 的枚举大多没有集中定义，且 `pending_rebuild`（C:107）在 B:171 的枚举中不存在。建议 C4 增状态字典表并对封闭枚举加 CHECK。
- **M1-16 与 M1-09 重复**（恢复语义两行主责）、**M1-05 多进程离线模拟与"M1 单实例"假设表述不一致**、**M0-06 把 M3 补偿写进 M0 通过标准**、**M0-09 把"决定权限矩阵"当验收**：建议拆行/移行，保持"每行唯一主责阶段"的自定规则。
- **首次发布/`GET /` 无活动版本形态**（`release_id:null`、`head_version:0`、`effective_for:none` 与 503 的边界）未定义。
