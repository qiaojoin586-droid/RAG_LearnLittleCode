# 《企业级 Agent 与模型配置热更新升级方案（2026-11-15）》审查意见

审查日期：2026-11-15。对象：[企业级Agent与模型配置热更新升级方案_2026-11-15.md](./企业级Agent与模型配置热更新升级方案_2026-11-15.md)（603 行）。

审查方式：只读审查，未修改原方案。逐节通读 + 对照当前代码库（factory.py、main.py、chat.py、task_runner.py、vector_store.py、rag_service.py、ppt_service.py、prompt_loader.py、config/prompt.yaml、ci.yml 等）+ 对照既有《多Agent与RAG企业化架构审查（2026-11-14）》与 `docs/设计方案（不可提交）/` 下相关设计文档 + 联网核验文内 10 个外部引用。文中行号均指原方案文档。

## 总体结论

方案整体质量较高，可以作为 M0/M1 的设计基线，但**当前版本不宜直接进入实施**。

优点（应保留）：

- 结构完整：17 章覆盖现状、架构、协议、数据模型、热更新、Ollama、Embedding、前端、API、安全、Agent 工作包、迁移、里程碑、验收、上线回滚。
- 现状事实基础可靠：§2 的现状陈述逐条对照代码，除"CI 含关键词评测"一行外均成立或仅有程度偏差（如"部分调用方"实为全部）；17 个文内相对链接全部可解析；10 个外部引用全部可访问。
- 热更新语义严谨：数据库活动指针为事实来源、不可变清单、请求快照、发布幂等、凭据与配置分离、不靠"清缓存"假装原子切换，这些约束在同类设计里属于较扎实的表述。
- 边界声明清楚：明确"只新增方案文档、未修改实现"、"验收矩阵是要求不是已通过结果"，避免了文档冒充证据。
- 安全红线明确：密钥不返明文、不落 localStorage、换 origin 不静默带旧 Key、模型端点策略独立于网页抓取策略。

主要问题集中在四类，共数十项，按优先级整理如下：

1. **事实性问题 7 项**（少数现状描述不准确或严重低估，需先改）；
2. **内部一致性与可验收性 7 项**（"第一阶段"边界、角色枚举、阶段与验收错配等）；
3. **数据模型与关键流程缺口 20 余项**（草稿、幂等、验证结果、管理员权限、地址白名单、价格版本、Outbox、凭据轮换语义等）；
4. **与既有审查/既有设计的对齐问题 8 项**（既有 P1 被搁置、"保留现状"与既有结论冲突、DashScope 迁移实测结论未继承等）。

建议修订顺序见第七节。修订后建议以"角色注册表 + 数据模型 DDL 草案 + API 契约表 + 里程碑验收矩阵"四份附件补强，再进入 M0。

## 一、事实性问题（P0：进入实施前必须修正）

### F1. §2 行 41 说 CI 含"关键词评测"，不属实

原文把 `.github/workflows/ci.yml` 与 `tests/eval/eval_runner.py` 并列，称 CI 有"测试、构建、依赖锁定与关键词评测"。

证据：`ci.yml` 只有后端 `pytest`、前端 `lint / vitest / tsc / build`，并安装 `requirements.lock`；**没有任何步骤调用 `tests/eval/eval_runner.py`**。该评测器是手动脚本：需要运行中的服务、依赖 `admin/admin1234` 登录、按 `expected_keywords` 判定，且通过率 ≥50% 才退出 0。

修正：改为"CI 有 pytest 冒烟、前端 lint/单测/类型检查/构建与锁定依赖安装；关键词评测是独立手动脚本（依赖运行中服务），不在 CI 中"。

### F2. §2 行 38 "部分调用方没有处理"实为全部 8 个调用点均未判空

原文："超限返回 None，部分调用方没有处理"。

证据：`spawn_background_task` 全部 8 个调用点都没有判空——`agent_middleware.py:141`、`chat_graph.py:166`、`chat.py:381/653/667`、`note_service.py:126/130/298`。其中最严重的是 `chat_graph.py:166-177`：任务为 None 时仍执行 `task.done()`/`task.cancel()`，抛 `AttributeError`，且结束哨兵永不入队，SSE 流会挂起（与既有审查 A5 结论一致）。

修正：写"全部调用方未判空；`chat_graph` 超限时抛 `AttributeError` 并挂起流，M0 必须修"。

### F3. §5.1 行 152 "PPT 大纲从当前大纲模型配置导入"不存在该配置

证据：`ppt_service.py:70-95` 直接读 `DASHSCOPE_CHAT_MODEL`（**与主对话同一变量**）与 `DASHSCOPE_API_KEY`，`base_url` 硬编码 `DASHSCOPE_BASE_URL`，完全不看 `MODEL_PROVIDER`，也没有独立的大纲模型环境变量。

修正：改为"当前复用主对话模型与 Key，导入后拆为独立 `ppt_outline` 绑定"。

### F4. §2 行 34 / §14.1 行 497 未点明 prompt 映射已有 3 条死链

证据：`config/prompt.yaml` 有 13 条映射，`prompts/` 只有 10 个文件，`rag_summarize`、`report`、`reorder` 三条无对应文件且代码从未加载；RAG 摘要实际是内嵌字符串（`rag_service.py:303-308`）。

影响：§14.1 第 4 步"校验 prompt.yaml 中映射文件是否存在"是正确要求，但实施时会"重新发现"这 3 条；建议直接列出已知清单与处置（删除或补文件），避免导入步骤被当作新增问题。

### F5. §14.2 迁移清单遗漏 5 个真实入口

| 遗漏入口 | 证据 | 影响 |
| --- | --- | --- |
| 回顾题生成 | `review_router.py:73-75` 直接注入 `init_manager.chat_model`；`review_service.py:289-317` | §5.1 行 155、§16 行 567 都要求"回顾"迁移，清单却没有这一行 |
| 后台定时任务 | `scheduler.py:35-40` 取 `init_manager.note_service`（间接持有模型） | §7.4 行 267 提到"定时任务"解析活动版本，清单无对应行 |
| 知识库上传/入库 | `knowledge_router.py:230-249、438-439` 经 `VectorStoreService` 用 embed_model | 只写"RagService / VectorStoreService"一行，容易漏改上传链路 |
| 手动 Embedding 迁移脚本 | `scripts/manual/migrate_embeddings_2560.py:53-60` 自建 `DashScopeEmbeddings` | 绕过工厂，实施后仍会读出旧 env 变量 |
| 标题生成的实际模型来源 | `chat.py:245` 当前用 `classifier_model` 生成标题 | 清单写"标题生成继承父请求配置版本"，未说明现状来源，迁移时角色绑定易错 |

另建议点名 `stream.py`/`chat_route.py`（思考事件、SSE 事件白名单）与 `.env.example` 中 9 个注释掉的 `OPENAI_*` 角色变量（"规划中"，代码不读取；导入步骤应识别并清理，避免与无前缀变量形成两套语义）。

### F6. §5.1 行 159 "CrossEncoder 重排序……第一阶段保留现状"与既有审查结论冲突

既有审查（2026-11-14）R2：`rag_service.py:242` 调用的 `compute_score` 在安装的 `sentence-transformers 5.6.0` 中不存在（本机核实：只有 `predict`/`rank`），当前重排序总是异常后静默降级为原排序。"保留现状"等于保留一条失效路径，而 §17 行 597 又要求"所有模型调用入口统一解析"。

修正：二选一——（a）M0 修复为 `predict` 并补"构造原顺序错误的候选，确认 reranker 改变顺序"验收；或（b）明确"重排序排除在模型配置之外，M3 统一检索时修复，M1 期间在页面与 trace 中标记为降级状态"。

### F7. §4.1 行 99 / §4.3 行 128 与锁定 SDK 的实际行为需要写实

- §4.1 行 99 写"不能由模型名或 SDK 隐式推断并切换协议"。但锁定版本的 `langchain-openai` 官方文档明确：设置 reasoning 相关参数时 `ChatOpenAI` 会**自动**路由到 Responses API。要实现这条纪律，必须写明"显式关闭 `use_responses_api`、不传 reasoning 参数，或用受控包装器"。
- §4.3 行 128 把 `reasoning_content` 是否被保留写成"迁移时必须验证"。既有《DashScope迁移OpenAI大模型接入设计方案》已给出实测结论（锁定版不保留），且该方案还指出 Responses 路径下 `chunk.content` 会变成 list、必须先改 `stream.py` 的 str/list 双形态。建议直接引用既有结论并列为 M1 必测项，而不是作为未知项重新验证。

## 四、流程与安全的未定义点（P1）

### G1. 凭据替换与在途请求语义未定义（安全核心）

行 196 `replace` 生成新凭据版本、行 257 缓存 Key 含 `credential_version`、行 247/249 发布与验证绑定凭据版本、行 427 回滚不得复活已撤销凭据——但未回答：

- replace 后，已经解析快照的在途请求用旧凭据还是新凭据？
- 旧凭据何时停止服务？旧 Key 被供应商撤销后在途请求如何失败、如何呈现给用户？
- 凭据替换是否必须伴随新 release？若是，§5.4 的"保存即生效"语义要相应改写。

建议给出三态（未解析 / 已解析未发出 / 已发出或流式中）与对应的凭据解析与中断规则，并与 "进行中的请求保持原快照"（行 20/230）对齐。

### G2. 紧急撤销只说"单独定义策略"，全文未定义

行 235 说紧急撤销"可阻止尚未开始的调用"、行 237 又说可"中断执行"，两处边界不一致；且没有操作入口、审计事件、与在途请求的关系。验收矩阵也没有紧急撤销用例。

### G3. 能力探测方法缺失

行 111 要求 CapabilityValidator 记录"支持/不支持/未验证"，行 243 要求发布前"小规模协议与能力探测……工具调用使用无副作用的测试工具"，但没有定义：

- 每个角色的最小探测请求是什么（工具调用能力如何在不产生副作用的情况下验证）；
- 判定标准（怎样算"支持工具调用"）、费用上限、失败重试；
- "未验证"的默认策略（行 123 要求工具型 Agent 必须验证，是否意味着未验证即禁止发布？）；
- 测试调用如何"单独标记"（需要 D10 的 `is_test` 字段）。

### G4. Embedding 语义同一性判定缺失

行 329 "更换 URL，但确认服务的是同一向量模型版本"、行 335/339 的 `semantic_fingerprint`——没有定义指纹的来源与计算方式（模型名+维度？固定探测文本的向量哈希？跨供应商同模型如何比对？相似度阈值？），而 §16 行 568 的验收依赖它。建议：固定探测文本集、保存向量哈希或余弦阈值、记录模型 revision（Ollama digest、供应商快照版本），无法确认一律新索引。

### G5. 发布探测范围过宽

行 243 对所有发布都做网络探测。提示词/绑定变更不涉及连接时也依赖供应商可用性，会让"改一个文案"受制于上游。建议明确"仅当模型连接、凭据或 origin 变化时必测；纯提示词/模板变更只做变量与契约校验"。

### G6. 运行时模型失败/降级的处理缺失

§7.1 表（行 226-236）只有发布期与凭据撤销场景，没有"运行时调用超时/429/5xx/工具调用失败"行；行 138 说跨供应商降级"绑定在已发布版本中"，但 release 的 `role_bindings` 没有 fallback/禁用字段。建议：role_bindings 增 `fallback`/`enabled`；定义超时、限流、5xx 的本地重试次数与失败呈现；显式保留现有同厂商角色级降级（分类/Plan 缺 Key 回退主模型、补全缺 Key 关闭），不要把"不自动跨供应商重试"读成取消既有降级链。

### G7. 向量存储部署模型没有决策

现有 `VectorStoreService` 是 Chroma `PersistentClient`（SQLite 本地文件、进程内单例，`vector_store.py:102-116`）。方案 §9.3 行 353 引入 Outbox Worker、M4 行 535 引入多实例 Worker，但没有说明向量库保持"嵌入式单实例"还是迁移为独立服务。若不决策，M3/M4 的 Worker 与多实例无法共享索引（既有审查 R9 也已指出）。建议在 §9 加"部署假设与决策点：M1—M2 单实例嵌入式；M3 前决定索引服务形态"，并写明数据迁移与回滚路径。

### G8. 提示词可编辑与"安全规则"保护冲突

行 216 只保证"编辑模板不改变工具权限、身份和资源归属"，但实际防注入安全规则硬编码在 `prompts/main_prompt.txt` 第七节"安全规则"和 `plan_generation.txt`；页面上可编辑全部系统提示词，意味着管理员可一键删除/削弱既有护栏。建议明确：安全段由服务端策略在发送前拼接，或发布时强制校验安全段存在；并把提示注入回归用例加入 §16。

### G9. 上下文窗口/分词器未进入模型版本

§5.4 行 191 的模型版本字段没有 `context_window`/`tokenizer`；当前 TokenBudget 读全局 `agent.yaml token_budget.model_context_size`（默认 32768），切换上下文不同的模型时预算会算错。建议 profile 增能力字段并由请求快照驱动 TokenBudget，M1 加"跨上下文模型切换"验收。

### G10. §11 API 契约不完整

缺少：`GET /drafts/{id}`（刷新/多标签恢复）、`DELETE /drafts/{id}`（放弃与过期）、测试结果读取（行 417 的 202 没有读取接口）、提示词版本列表/详情/恢复默认、M1 的 Embedding 只读状态（行 371 页面要求，但接口标 M3）、`GET/PATCH` 中的 Key 状态字段（行 375 的 `has_api_key`/末尾标识/凭据状态未落到契约）、分页参数、幂等键位置、错误码到端点映射、409/422 的响应示例。建议补 OpenAPI 或契约表，并把发布响应的 `effective_for` 等字段定义为枚举。

### G11. 缺少"恢复历史版本"的 M1 验收行

§10 行 373、§11 行 393 有"恢复某版本"，§17 行 585 有回滚策略，但 §16 只有索引回滚（M3）。建议补：切回旧发布后新请求生效、进行中请求不受影响、凭据预检失败时保持当前指针、审计记录恢复来源。

### G12. 权限粒度与敏感操作防护

行 165 只说"管理员"，未区分读敏感详情 / 测试 / 发布 / 回滚 / 读审计的权限；Key 提交与发布属于高敏感操作，建议补权限矩阵、二次认证（reauth）与 CSRF 防护说明。

### G13. Ollama 细节缺口

§8.1/§8.3 未覆盖：原生 Embedding 端点应为 `/api/embed`（旧 `/api/embeddings` 已从官方参考移除，访问 404）；原生 `tool_calls` 与流式事件到统一事件契约的映射；模型发现端点差异（原生 `/api/tags` vs 兼容 `/v1/models`）；`keep_alive` 与上下文对内存/并发的影响；兼容模式 `dimensions`、`encoding_format` 支持范围。建议 §8 增加"协议端点与事件映射表"。
