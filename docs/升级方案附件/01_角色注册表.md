## A2. 发布清单的绑定结构

```json
{
  "schema_version": 2,
  "role_bindings_raw": {
    "chat": {
      "enabled": true,
      "selection": "explicit",
      "profile_revision_id": "profile-chat-uuid",
      "credential_revision_id": "credential-uuid",
      "prompt_revision_id": "prompt-main-uuid",
      "fallback": [],
      "failure_mode": "error"
    },
    "session_title": {
      "enabled": true,
      "selection": "follow_role",
      "source_role": "classifier",
      "prompt_revision_id": "prompt-title-uuid",
      "fallback": ["chat"],
      "failure_mode": "default_title"
    }
  },
  "index_bindings": {
    "notes": {
      "index_version_id": "index-notes-uuid",
      "query_profile_revision_id": "profile-embedding-uuid",
      "credential_revision_id": "credential-embedding-uuid"
    }
  }
}
```

此 JSON 是结构示例，不是可发布的完整清单。v2 新草稿/发布需包含全部 17 个角色，每项明确 enabled；关闭的项也不能消失。prompt_revision_id 对 embedding 必须为 null，其余项必须指向本角色允许的模板契约。

selection 仅为 explicit、follow_role、follow_execution。follow_role 要求 source_role，禁止环；发布器只将 follow_role 编译到 resolved_static_bindings，并保存完整反向引用；follow_execution_roles 在发布时只记录动态角色，实际模型在请求中解析和追踪，不能伪称已静态选定。follow_execution 只允许 synthesize 使用，解析为本轮附件/思考路由实际选中的模型，仍使用 synthesize 自己的提示词。页面独立修改会转成 explicit，并显示修改影响范围。

credential_revision_id 在 profile、解析后绑定和索引绑定之间必须相符；无认证为 null。不得在运行时把它替换为“最新凭据”。fallback 是清单内角色的有序白名单，不接受 URL；检查无环、权限、能力、上下文和数据出站范围。classifier 的 rule_only、planner 的 react_fallback、autocomplete 的 disabled 和标题 default_title 均为明确 failure_mode。

## A3. 最小能力探测与发布判据

| 能力 | 最小探测 | 通过条件 |
| --- | --- | --- |
| 文本/流式 | 固定无个人数据短消息，消费到终止事件 | 有正文、流可结束、错误归一；不只检查 HTTP 200 |
| 工具调用 | 本地 echo_test，参数含随机 nonce；接收 tool call 后本地执行并回传结果 | 名称与 JSON 参数匹配、call ID 可关联、后续回答使用结果；不调用真实业务工具 |
| 结构化输出 | 固定两字段 JSON 或 Schema 请求 | 严格解析并满足当前角色输出契约；文本 JSON 降级明确标识 |
| 图片/视频 | 无个人数据的固定测试图片；视频另测抽帧或原生输入 | 分别记录能力；图片通过不代表视频通过 |
| 思考控制/扩展流 | 固定短请求，分别测试支持的控制参数 | 控制不报错；可用摘要/进度按协议归一；不要求返回隐藏推理过程 |
| Embedding | 固定双文本批次 | 数量、维度、有限浮点值、输入次序与编码符合约定 |

单次验证任务默认最多 3 次模型请求、每次最多 96 输出 Token、云端总截止 30 秒；本地冷启动预算可显式设为 90 秒，计入队列等待。默认不自动重试；用户重新测试创建新验证记录。价格已知时同时使用金额预算，价格未知时显示未知费用并用调用数/输出上限约束，不能宣称有严格金额上限。

结果为 supported、unsupported、unverified；只有成功的必需能力允许新启用角色发布。断网、超时、无额度产生 unverified，不能改写为确定不支持。连接、凭据、协议、必需能力或目标模型改变时测试；纯提示词文案改变只进行变量、固定安全策略和输出契约静态校验。绑定到已验证且兼容的版本可复用结果，绑定首次启用的新能力则补测。

验证保留 target_spec、hash_algorithm 和 target_hash：精确规范化输入与 JCS/SHA-256 算法见附件 C §C3，包含 endpoint_policy_revision_id、安全策略和 probe_suite 版本；默认有效期 24 小时。失效结果不可作为新连接发布依据；纯历史发布恢复的离线预检例外见附件 C §C3.1，不因供应商故障阻止合法回滚。测试调用 is_test=true，计入独立用量分类，不计入用户正常业务成功率。

## A4. 协议和内容归一

M1 默认 Chat Completions。管理员显式选择 `api_protocol=responses` 并验证通过后，该角色才请求 `/responses`。后端根据发布快照选择路径，参数沿用白名单。Responses 流只输出回答文字、已完成的函数调用和用量，使用 `call_id` 关联工具结果。

锁定 langchain-openai 1.3.5 的现有专项实测已经指出 reasoning_content 不透传。M1 对这类扩展采用供应商包装器或明确关闭进度显示；不能继续将此项当作未知事实。stream.py 统一接受 content 的字符串和内容块列表，提取正文及可用摘要，过滤未知块，保持工具 call ID；chat_route.py 白名单登记新事件。M1-R02/M1-17 覆盖两条协议路径，协议未启用也要离线验证内容块不会导致 TypeError。

OpenAIEmbeddings 显式传 base_url；兼容端点默认 check_embedding_ctx_length=false，将文本而非 OpenAI 分词 ID 发给异构服务，由服务端受控切片限制长度。dimensions 是否发送按供应商和模型验证：OpenAI 的相应参数适用于 text-embedding-3 及其后支持该参数的模型，不能把这一限制推广为 Ollama 等全部服务商的限制。[OpenAI Embeddings 参数](https://developers.openai.com/api/reference/resources/embeddings/methods/create)

encoding_format 默认 float；只有端点实测支持时才启用 base64 并解码为统一向量。模型版本记录 context_window、tokenizer_id、tokenizer_revision、计数策略、输出上限和图像预算算法，请求 TokenBudget 从快照构造；未知 tokenizer 使用保守计数并留安全余量，不继续沿用全局 32768。

## A5. M1 原生 DashScope 向量兼容

adapter_type=dashscope_native、api_protocol=dashscope_embed、auth_mode=dashscope_key，M1 保留原生协议与 document/query 参数，不自动转成兼容端点。源模型修订不明时继续标 baseline_unverified 并保留原组合，不能由模型名+维度伪造已证实的空间指纹。

锁定社区封装在初始化写全局 dashscope.api_key，embed 调用未逐次传 Key；直接复用它会破坏独立配置和在途凭据版本。新适配器保留向量语义，以 SDK 逐次显式 api_key/base_address 调用和受控传输包装实现，不能依赖全局 Key/URL。SDK/tenacity/httpx 的重试统一计数，约束见附件 C §C6。M1-R08 验证双版本 Key、原生 document/query、未改空间和真实出口策略；兼容端点转换仅列 M3 重建候选。

可写字段以附件 E 的 ProfileInput/RoleBinding 为准。adapter_type 三类、api_protocol 六类与附件 B CHECK 同步。A2 给出部分结构示例，完整草稿和发布清单由附件 E 校验。ReleaseManifestRead 接受 v1/v2/v3。从 v1 克隆或恢复时在新记录中补入禁用的 memory_extraction。

## A6. M3 查询扩展角色

M1 的 v2 草稿含 17 个角色。在模型配置页首次保存“检索查询扩展”会将该草稿升级为 v3，并加入第 18 个角色 `rag_query_expand`。它使用独立配置档、凭据绑定和提示词，模板变量只有 `{query}`。服务端运行开关和已发布角色须同时启用。2026-11-24 的本地采用决定将运行开关保持关闭。[附件 G](./10_RAG四层架构与多路召回设计.md)

CrossEncoder 仍是独立能力，M3 选择及版本需登记，不能将本地打分器伪装为 OpenAI 聊天模型；LLM 重排和知识图谱查询没有因参考图自动成为默认角色。
