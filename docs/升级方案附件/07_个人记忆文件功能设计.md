## F1. 范围与可行性判断

可行，纳入 M1 的个人记忆增量。每名登录用户有一份逻辑文件 memory.md，跨自己的会话使用；所有模型读取同一个已选择版本，不按供应商复制文件。模型、URL、Key 和各角色提示词仍由模型配置页面管理，个人记忆不提供这些管理权限。

本次交付包括首次自动创建、自动提取、手工编辑、生成建议、版本恢复、下载、停用与清空。当前会话的 memory_summary 是短期历史摘要，继续独立存在；向量化长期记忆、语义检索、多文件目录和组织共享记忆仍在 M4，不因新增 Markdown 文件提前启用。

产品表现为文件，后端以 MySQL 中的版本化 Markdown 文本为权威来源。下载时输出 UTF-8 memory.md；不依赖某台应用服务器的可变本地文件，不使用客户端传来的路径，也不把它当成 AGENTS.md、SKILL.md 或可执行配置加载。数据库、日志与备份按个人内容管理，文件名不代表存储路径。

## F2. 页面和入口

头像菜单顺序：个人信息 → 用量 → **记忆文件** → 设置 → 关于。独立登录路由 `/memory`，沿用应用布局；按当前代码修改点是 `front/src/components/layout/UserAvatarMenu.tsx` 和 `front/src/router/index.tsx`，不是在模型配置中混入每人的内容。

页面包括：

| 区域 | 行为 |
| --- | --- |
| 文件标题与状态 | memory.md、当前修订号、更新时间、自动/手工管理、已启用/已停用、生成中/生成失败 |
| Markdown 编辑器 | 全文可编辑；编辑/预览切换、字节数、未保存提示、保存和取消；无强制不可编辑的正文区域 |
| 使用控制 | “在 AI 助手中使用”“允许自动提取”；停用后内容仍可查看/编辑，保存不会擅自重新启用 |
| AI 建议 | 与当前版本的差异、来源会话/时间、采用/忽略；过期建议提示重新生成，不覆盖新版本 |
| 历史与操作 | 分页历史、查看/恢复、下载、清空并停用；恢复创建新版本，不回拨修订号 |

无文件时 GET 返回 `exists=false` 和模板预览，不因访问页面写库；首次使用 AI 自动创建，用户也可直接保存预先创建。保存成功显示“下一轮生效”；409 冲突保留本地草稿并提供加载新版本/手工合并，禁止自动以本地全文覆盖。

预览默认禁用原始 HTML、脚本、事件属性和危险 URL；外部图片/嵌入资源不自动加载。编辑器、下载和错误提示均不执行 Markdown 中的代码、链接或工具指令。切换用户时清除编辑缓存，草稿不存无用户隔离的 localStorage。

## F3. 创建、提取和手工内容保护

### F3.1 首次使用

1. 已认证的主 AI 助手请求完成权限、额度和请求格式校验后，在接入模型之前读取个人记忆 head；未创建且允许使用时，以用户唯一键在短事务中创建 head 与第一版模板，重复受理不产生重复文件。
2. 首次模板只含“回答偏好 / 长期背景 / 持续事项”等空标题，不推断姓名、身份、职业或事实。首轮使用空模板，不能把尚未完成的本轮提取结果当成已有记忆。
3. 用户消息持久化且主回答成功后，事务化插入提取任务；后台从用户自己明确表达的稳定事实、长期偏好或“请记住”内容生成候选。无值得保存的信息则 `no_change`，不制造更新。
4. 提取任务失败只影响记忆状态，已成功的主回答保持成功；页面可重试。启用状态下，模型调用前读取/创建失败返回明确可重试错误，不静默假装使用了记忆。

默认首次创建为 `management_mode=auto`、`enabled=true`、`auto_extract=true`。未创建用户的设置也需要持久化 head：用户先停用时创建无 active_revision 的 head，后续 AI 请求尊重停用状态。`memory_mode=off` 的单轮请求不读取正文、不创建文件、不触发提取，但仍执行已有的身份/额度检查。

### F3.2 自动更新和手动修改

自动模式下，候选只有在 `base_revision_id + expected_head_version + memory_epoch` 与当前 head 全部相符时才能提交。用户任何一次手工保存、采用建议或恢复历史都切到 `manual`；后续 AI 提取仅产生建议，不直接写活动内容。用户可显式切回自动管理，页面说明此后允许 AI 更新全文；切换同样递增 head_version，使旧任务失效。

手工模式的采用操作校验建议归属、基线与 epoch，创建新 revision 后原子移动 head。基线已变返回冲突，禁止后台无提示重算并覆盖手工文件。用户可以继续自由编辑全文，不用遵守机器保护区或特殊注释格式。

提取仅输入本次已持久化的用户原文和本人选定的记忆版本，以及服务端提取规则；不自动输入系统提示词、API Key、工具输出、其他用户内容、附件全文或 AI 回答。提取器输出符合 `MemoryExtractionResult` 的结构，并为新增/修改事实给出本次用户消息证据片段；服务端检查引用属于输入。模型输出不能直接执行工具、写文件或发请求。事实真伪不能只靠 Schema 证明，需冻结事实提取/污染评测集。

默认拒绝把疑似凭据、认证 Token、一次性验证码等自动写入记忆；手工保存命中明确凭据模式时返回字段级错误，不把原值写日志。无法保证识别全部敏感内容，页面持续提示“此内容会随提问发送到当前配置的模型服务”。不把完整聊天记录、隐藏推理或每次问题原样长期复制进去。

### F3.3 持久任务和有界资源

`user_memory_jobs` 是 M1 自带的持久提取队列，同进程轮询消费，不依赖当前内存后台任务队列，也不以等待 M2 为理由丢任务。唯一 `(user_id, source_request_id)` 防止重放重复生成，source_request_id 为原业务请求 32 位 hex；source_message_id 对应当前 ChatMessage 的 INT 主键，服务端验证所属会话和用户。

同源重复受理返回已有 job；显式重试 failed/obsolete/cancelled 的同源任务前验证来源仍授权且未过期，锁 head/job 后递增 generation_number、重置基线/租约/预算，旧 Worker 的结果不得落库。其他终态不重复提取；手动 generate 返回该终态的 200 元数据。任务固定触发时的 config_release_id、提取角色/提示词版本、基线记忆与最小化来源。每任务最多 2 次模型尝试，单次 60 秒、总截止 180 秒（包括排队）；每用户最多 1 个运行任务、5 个待处理任务，超限记录 skipped_limit，主回答不回滚。同用户按创建顺序认领；旧基线不得自动重试应用。提取输入/输出限额及费用进入用量分类 `memory_extraction`，与主回答分开，复用已发布的出站授权及总重试约束。

状态为 queued/running/proposed/applied/no_change/failed/obsolete/cancelled/skipped_limit；lease 到期可有限恢复，已出站但结果未知不重复计为成功，应用候选仍受唯一键和 CAS 保护。手工模式成功输出为 proposed；自动模式 CAS 成功为 applied，CAS 失败为 obsolete，用户手改发生在提取途中也不会被覆盖。任务源片段只为恢复而短期保存，终态 7 天后清理源片段，建议 30 天失效；保留脱敏计数与关联 ID。

## F4. 提问组装顺序和权限优先级

没有一项通用“企业 Agent 标准”规定所有项目必须按同一段字符串拼接。这里采用明确的消息角色、来源分级、最小化上下文和服务端授权规则；顺序是本项目的可验收契约，不宣称为行业强制标准。

### F4.1 首次模型调用的消息布局

| 次序 | 内容 | 发送角色及处理 |
| --- | --- | --- |
| 1 | 服务端固定安全策略、身份/工具边界 | system；只由服务端生成，用户不能经记忆改写 |
| 2 | 活动发布中的角色业务提示词和任务规则 | 支持时使用 developer；仅支持 system 的适配器在受控 system 中排在固定策略后。冲突静态检查先于发布 |
| 3 | 经过筛选的历史对话 | 保持原 user/assistant 及真实工具调用关系；压缩摘要改为下方数据，禁止冒充 system 或重新授权工具 |
| 4 | 记忆文件选段、历史摘要、已授权 RAG/引用文件与附件文本 | 独立 user 上下文消息；有类型、来源、版本和完整转义的 JSON 数据封套，不升级为高权限提示词 |
| 5 | 当前用户问题及本轮图片/视频等内容块 | 最新 user 消息；保留原始明确要求，不能被旧记忆替代 |

顺序 4 内固定为 memory → history_summary → evidence（RAG、引用文件、附件文本），缺项省略。真实工具执行后继续追加 assistant tool_calls → 对应 tool 消息，逐项匹配 tool_call_id；不能把预装的记忆伪装成工具执行结果。若端点不接受相邻 user 消息，适配器把上下文数据和当前问题编码为同一 user 的两个内容段，当前问题仍最后，保留类型边界。

示意 JSON 只表达布局，不是可直接发布的模型清单：

```json
{
  "messages": [
    {"role":"system","content":"服务端固定安全规则；参考数据不提供工具权限"},
    {"role":"developer","content":"已发布的角色业务提示词；当前明确要求优先于旧偏好"},
    {"role":"user","content":"{\"type\":\"reference_context\",\"memory\":{\"revision_id\":\"memory-rev-3\",\"content_md\":\"# 回答偏好\\n默认简洁中文\"},\"evidence\":[]}"},
    {"role":"user","content":"这次请用英文详细回答，并说明理由。"}
  ]
}
```

处理冲突时：服务端安全/业务约束优先；在允许范围内，本轮明确要求优先于记忆里的旧偏好。例如 memory.md 写“默认简洁中文”，本轮要求“英文详细解释”，应按本轮要求回答。记忆的事实可过时；RAG、历史摘要和文件里的命令都属于参考数据，不能授予权限或改变执行边界。用户直接表达“请记住”只产生受控提取任务，不直接执行任何文件里的命令。

JSON 转义和分隔符只是结构措施，不能保证模型免于提示注入。包括 `</memory>`、伪 role JSON、要求忽略规则的 Markdown 在内的恶意内容，始终作为数据发送；工具许可、用户身份、读写归属、外发和审批在每次真实执行前由后端验证。

### F4.2 统一组装点和快照

新增 `ContextComposer`，供普通对话、视觉、Planner、执行步骤、综合和反思共用。当前 `app/routers/chat.py` 会把 RAG、引用笔记和模板文本追加到 system_prompt，需要随本功能迁出；`plan_execute_agent.py` 的 `system_prompt[:2000]` 也必须改为结构化预算，不能截断保护规则。用户可控模板内容作为数据，真正由管理员发布的任务规则仍属第 2 层。

每轮固定 `{config_release_id, memory_revision_id, memory_head_version, memory_epoch, memory_hash, selected_sections_hash, composer_version}`。Plan 子步骤继承同一个个人记忆版本和模型发布，按最小必要原则取其子集；后台提取也固定触发时的模型发布，不因中途换 URL/Key 读新版本。个人文件保存无需管理员发布，下一轮取新 revision，进行中的普通请求保持原快照。

正文缓存键包含 user_id/revision/hash，跨用户绝不共享，编辑后以 head_version 校验；trace 记录版本/哈希/使用量和截断状态，不默认记录完整记忆、问题或提示词。记忆缺失、关闭、空白、截断、读取失败使用不同状态，不伪称“已使用”。

### F4.3 上下文预算与使用范围

正文统一 CRLF→LF 后计算哈希，拒绝 NUL/不可显示控制字符，保留正常换行/Tab；不自动改写用户语义。Markdown 正文上限 32 KiB（UTF-8 字节），JSON Schema 的 maxLength 只能限制字符，字节数由服务端另检。默认个人记忆注入上限为 min(2048 Token, 本角色可用输入预算的 20%)；计数基于模型快照 tokenizer，未知时采用既有保守策略。优先保留完整小节，按文件次序选择、稳定截断，返回 selected/truncated/omitted 状态及选段哈希。页面注明保存文件不代表每轮全文都发送。

先保留固定规则、必要任务要求、当前问题与输出余量，再分配记忆/摘要/证据/历史预算；预算不足依次减少旧历史、低排名证据、摘要和记忆。不能静默截断当前问题或安全策略；仍放不下时明确报上下文超限。引用的其他文件按已有权限与预算选择，memory.md 中的链接不会自动抓取。

| 角色/入口 | 个人记忆策略 |
| --- | --- |
| chat、chat_thinking、vision | 主助手读取本轮选段；每次成功主回答最多触发一个提取任务 |
| planner、synthesize、reflection 及执行子步骤 | 继承主请求快照，限任务相关选段，不再触发提取；未来支持独立主入口时也走同一策略 |
| classifier、session_title、autocomplete、auto_tag、ppt_outline、write_assistant、review_question、rag_summarize、embedding | 默认不自动注入个人文件；新增用途须显式登记消费范围、预算和验收，不能全局拦截所有模型调用 |
| memory_summary | 只压缩被授权的会话历史，不把个人记忆混进压缩来源，避免重复累计 |
| memory_extraction | 只接收 F3 定义的来源与基线，不递归触发记忆生成，也不获取工具权限 |

## F5. 与模型配置、Ollama 和热更新的兼容

新增独立业务角色 `memory_extraction`，高级区显示“个人记忆提取”，使用自己的 `memory_extraction` 提示词和 `MemoryExtractionResult` 输出契约；可单独配置 URL、Key、模型或显式 follow_role=classifier，不能与 memory_summary 混用。旧配置升级时默认禁用，不悄悄增加云端调用；管理员完成配置和结构化输出探测后启用，页面才显示自动提取可用。角色未启用时仍自动创建空模板并允许手工编辑，状态为 extraction_unavailable，不伪称已自动学习。

OpenAI 兼容端点仍走 Chat Completions，Responses 必须显式开启，记忆功能不改变协议选择。Ollama 原生 `/api/chat` 与兼容 `/v1/chat/completions` 均由后端发送同一上下文；原生用 system/user/assistant/tool 可支持的角色映射，不能假定 developer 可用。原生 format/兼容结构化输出需实测；无原生 Schema 支持可选择严格 JSON 文本解析及至多一次有预算的修正，不能把任意自由文本直接写入记忆。URL、无 Key/反向代理 Key、内网授权、冷启动与 Token 预算继续执行主方案 §8 和附件 C，不把 Ollama 模型名称当能力证明。

配置清单由 schema_version=1 的 16 角色升级为 schema_version=2 的 17 角色；附件 E 保留 `LegacyReleaseManifest`/`ReleaseManifestRead`。历史 v1 发布不可修改，允许读取和固定快照执行，缺失提取角色时按 extraction_unavailable 处理；从 v1 克隆草稿或恢复时，确定性补入禁用的 memory_extraction 并编译成 v2，再走既有校验/CAS/审计。部署回退到只认识 v1 的旧程序前，须先切回 v1 兼容发布并停用记忆入口/任务；否则拒绝旧程序启动，不能让旧实例误读 v2。个人记忆内容不放进系统模型 release，改文件也不触发能力探测。

## F6. 数据、API 与冲突语义

[附件 08](./08_个人记忆文件DDL.sql)在附件 B 之后增加 4 表，保持 B 的历史验证哈希；仍需转成 Alembic 并用真实旧库夹具验证。

| 表 | 责任 |
| --- | --- |
| user_memory_heads | 用户唯一活动指针、head_version、单调 revision_number、enabled、auto_extract、management_mode、memory_epoch |
| user_memory_revisions | 不可变正文/哈希/来源/父版本；所有引用带 user_id 复合约束，恢复产生新版本 |
| user_memory_jobs | 持久提取、租约/截止/预算、来源和基线、候选/错误及状态；release 固定引用 |
| user_memory_requests | 用户操作幂等；同键不同规范化请求哈希冲突，成功结果/失败结果可重放，规范化请求使用服务端 HMAC-SHA-256（含 action/If-Match/正文等）并记录密钥版本，7 天窗口 |

所有权只取当前认证用户，URL/body 不接受 user_id。普通用户访问自己的记忆，不要求 config_admin；模型管理员身份不自动允许读他人个人内容。分页对象、revision/job ID 和下载均二次验证归属，越权与不存在统一返回 404。读取及写入均 `Cache-Control: private, no-store`，沿用现有 Bearer/CSRF 条件和账号停用检查。

公共前缀 `/api/v1/user/memory`，统一 code/message/data/request_id，错误兼容 detail。列表默认 20、最大 100，游标与用户/过滤条件绑定。所有写请求需 Idempotency-Key；修改现有 head 需 `If-Match: "memory-<head_version>"`，未创建对象使用版本 0。鉴权后先检查幂等重放，再检查 CAS，避免成功重试被旧 If-Match 错判冲突。

| 方法/路径 | 请求与返回/语义 |
| --- | --- |
| GET `/` | MemoryDocument；无文件也 200，exists=false、revision_id=null；返回 ETag/head_version/settings，不写库 |
| PUT `/` | MemorySaveInput 全文保存，200 + 新 MemoryDocument；任意手改进入 manual；首次保存允许 head_version=0 |
| PATCH `/settings` | MemorySettingsInput，200；启停/自动提取/管理模式可分开，至少一项；递增 head_version |
| GET `/revisions`、`/revisions/{id}` | 仅本人历史元数据/单版正文；列表不返回所有正文 |
| POST `/revisions/{id}/restore` | 空对象请求；CAS 创建新版本，200，不重新启用已关闭状态 |
| GET `/download` | 当前版 text/markdown; charset=utf-8，固定 attachment filename=memory.md；不存在 404 |
| POST `/generate` | 空对象请求；基于当前 head 与最近一次未过期、已授权的成功主请求来源生成，202 + job_id；无来源 422；同源终态/重试见 F3.3，不同键且已有活跃任务返回 409 |
| GET `/jobs`、`/jobs/{id}` | 本人任务/建议状态，当前活动 job 可轮询，不暴露底层异常/凭据 |
| POST `/jobs/{id}/apply`、`/jobs/{id}/dismiss` | 空对象请求；采用校验建议原基线并写新版本，忽略只改变任务状态；均 200，过期建议不能采用 |
| POST `/clear` | MemoryClearInput，清空并停用，200；默认保留可恢复历史，purge_history=true 时事务删除历史/候选/来源正文，仅留无正文审计和空版本 |

空对象请求也拒绝未知字段；所有写操作按用户限流（默认 30 次/分钟），generate 单独 3 次/10 分钟。`generate` 不从其他会话拼接整段历史，也不使用最后一次 assistant 文本；auto_extract=false/角色不可用时明确失败，手工管理允许生成建议。请求记录不存全文；重放按结果 revision 受控读取，已彻底清理的旧正文返回 41040，不从备份/日志复原。幂等窗口 7 天，过期同键不当新操作执行；清理完整记录后保留键哈希墓碑至 30 天，之后才允许重用。

| --- | --- | --- |
| MEMORY_VERSION_CONFLICT / MEMORY_PROPOSAL_OBSOLETE | 40940 / 40941；409 | 保留本地草稿，返回当前版本元数据，不返回他人内容 |

| MEMORY_NOT_FOUND | 40440；404 | 包括他人 revision/job |
| MEMORY_RESULT_PURGED | 41040；410 | 幂等结果对应的旧正文已彻底清理，只返回脱敏元数据 |

### F6.1 写事务与清空边界

普通保存：认证/幂等重放 → 锁 user head（首次唯一插入）→ 校验 If-Match → 分配单调 revision_number → 插入 revision → CAS 更新活动指针和 head_version → 写幂等结果 → 提交。全程无外部模型调用；不使用 MAX+1。API 的设置/恢复/采用/清空使用同一事务约束。

停用使用或停用自动提取、清空、历史彻底清理时递增 memory_epoch，使旧任务/缓存失效；取消 queued/proposed，running 尽力取消并在落库前再次校验 epoch。普通正文编辑只改变 revision/head_version。下一次尚未发送的子步骤/模型请求取得出站许可前核对 epoch；不一致取消该运行并提示重新发起，避免继续外发已停用/清空的记忆。与清空并发但许可已先提交的请求可能已经发到上游，只能尽力取消，不能宣称远端内容可撤回。

默认“清空并停用”保留历史，页面必须说明仍可恢复；“同时删除历史内容”才是 purge_history=true。彻底清理需要在取消任务/epoch 变更的同一事务内断开指针并删除旧正文、建议和任务来源正文，写新空版本；请求幂等只留 hash/结果 ID，不留全文。审计和历史备份按批准的保留/销毁周期处理，不承诺线上删除会同步抹除离线备份。旧模型结果永远不能复活被清理的内容。
