# 对话执行检查点

2026-11-18 实施 M2-01 的持久状态基础。继续使用本地 MySQL，LangGraph 仍负责请求内编排。应用在业务边界写 SQL 检查点，状态格式受项目控制。`ChatRouteContext` 内的模型、客户端、通知队列、提示词和中间结果留在内存中。正式 Worker、凭据复核后恢复执行及任务级预算仍属后续范围。

流式对话在进入执行阶段时创建一条 `workflow_runs`，关联已提交的用户消息并固定当时的发布版本 ID。流程选定 ReAct 或 Plan 后写入路由，Plan 的每条步骤结束事件追加步骤编号。`finished_steps` 表示收到步骤结束事件，也涵盖返回局部失败结果的步骤。每次有效检查点增加 `state_version`。租约每 10 秒续期，有效期 45 秒，租约续期无检查点版本增量。

有助手回复时，成功状态和助手消息在同一事务提交。仅在提交后更新会话消息缓存并发送 `done`。执行失败或流关闭时尽力保存失败或取消状态。进程异常退出时，租约到期后读取接口将未完成记录呈现为 `interrupted`，保留原路由与步骤编号。过期租约无法再写成功状态。

聊天首个进度事件及 `done` 带 `workflow_id`。登录用户可通过 `GET /api/v1/chat/workflows/{workflow_id}` 读取自己会话的检查点，其中包括 `status`、`release_id`、`route`、`finished_steps`、`state_version`、源消息和已完成回复的 ID。其他用户及已删除会话的记录返回 404。查询只读取运行记录，适用于当前无活动发布的情况。API 返回 `Cache-Control: no-store`。
