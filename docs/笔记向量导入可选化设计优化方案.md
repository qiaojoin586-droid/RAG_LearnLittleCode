## 1. 现状分析

### 1.1 当前自动入库链路

```
用户创建/更新笔记
    │
    ▼
note_router.py → note_service.create_note() / update_note()
    │
    ├─ ① MySQL 写入（主流程，同步）
    │
    └─ ② spawn_background_task(_sync_to_vector(note))  ← 异步后台
           │
           ▼
       vector_store.upsert_document(
           documents=[note.content or note.title],
           metadatas=[{user_id, note_id, title, category}],
           ids=[f"note_{note.id}"],
           collection="notes",
       )
```

**触发点（共 5 处）**：

| 触发场景 | 代码位置 | 向量操作 |
|---------|---------|---------|
| 创建笔记 | `note_service.py:103-104` | `_sync_to_vector(note)` → upsert |
| 更新笔记 | `note_service.py:274-276` | `_sync_to_vector(note)` → upsert |
| 软删除笔记 | `note_service.py:308-313` | `delete_note_vectors(note_id)` |
| 恢复笔记 | `note_service.py:392-408` | `upsert_document(...)` 直接重建 |
| 彻底删除 | `note_service.py:440-444` | `delete_note_vectors(note_id)` |

### 1.2 RAG 消费端

```
AI 对话 → rag_service.query()
    │
    └─ 阶段 3：双源检索
         ├─ vector_store.search_documents(hyde_text, user_id)  ← 知识库
         └─ vector_store.search_notes(hyde_text, user_id)      ← 笔记库 ★
              │
              └─ notes_collection.query(where={"user_id": user_id})

Agent 工具 → search_notes_tool(query, top_k)
    │
    └─ note_service.semantic_search(db, user_id, query, top_k)
         └─ vector_store.search_notes(...) → 提取 note_id → MySQL 回填
```

**关键事实**：`search_notes` 仅按 `user_id` 过滤，**无法区分用户是否希望该笔记参与检索**。一旦笔记写入 ChromaDB，就会出现在 RAG 检索结果中。

### 1.3 问题总结

| 问题 | 影响 |
|------|------|
| 临时备忘、草稿等无检索价值笔记自动入库 | 浪费 Embedding API 调用 + ChromaDB 存储 |
| 用户无法控制哪些笔记参与 RAG | 不相关内容干扰检索结果，降低 AI 回答质量 |
| 缺少 `is_indexed` 状态标记 | 无法在前端展示哪些笔记已入库、哪些未入库 |

## 3. 后端改动

### 3.1 数据模型变更

#### 3.1.1 `notes` 表新增字段

**文件**：`app/models/note.py`

```python
class Note(Base):
    # ... 现有字段 ...

    # 是否导入向量库（参与 RAG 语义检索）
    # True = 已同步到 ChromaDB，参与 search_notes / RAG 检索
    # False = 未同步，不参与语义检索（关键词搜索 keyword_search 不受影响）
    is_indexed: Mapped[bool] = mapped_column(
        Boolean, default=True, nullable=False, server_default=sa.text("1")

```

**设计决策**：

| 决策 | 选择 | 理由 |
|------|------|------|
| 字段类型 | `Boolean` 单字段 | 比关联表简单，覆盖 95% 场景；无需记录同步时间/失败原因等元信息 |
| 默认值 | `True` | **向后兼容**：存量笔记全部视为已入库，行为与改造前一致 |
| 字段位置 | Note 模型顶层 | 与 `is_pinned` 同级，属于笔记基础属性 |

### 3.3 `note_service.py` 向量同步逻辑调整

#### 3.3.1 `create_note` — 条件判断

```python

    logger.info(f"笔记未标记为索引，跳过向量同步: note_id={note.id}")
```

#### 3.3.2 `update_note` — 条件式 spawn（传内存对象）

> **⚠️ R1 修复**：v1.1 将 `update_note` 改为自愈任务，但 create/update 路由是 service 返回后 router 才 commit（`note_router.py:56-59`），自愈任务可能在新 session 中读到未提交的旧内容。恢复 v1.0 的**条件式 spawn**（传内存对象，携带新值，无重读竞态）。
>
> **为什么安全**：`update_note` 路径中 `is_indexed` 不会变（I2 已将其移出 NoteUpdate），所以不存在「commit 失败但向量已操作」的 S1 风险——S1 仅存在于 `toggle`/`set` 路径（已在 §3.4.1 修复）。

```python
# 现有代码（line 273-276）：
# if self.vector_store:
#     spawn_background_task(self._sync_to_vector(note), name="note_update_sync_vector")

# 改为（条件式 spawn，传内存对象）：
if self.vector_store:
    if note.is_indexed:
        # 已标记索引 → 同步/更新向量（传内存对象，携带最新内容，无重读竞态）
        spawn_background_task(
            self._sync_to_vector(note), name="note_update_sync_vector"
        )
    else:
        # 未标记索引 → 确保 ChromaDB 中不存在
        spawn_background_task(
            self._remove_from_vector(note.id), name="note_update_remove_vector"
        )
```

> **设计原则**：`update_note` 路径的 `is_indexed` 不变（前端不通过 update 接口改该字段），所以传内存对象的条件式 spawn 无 S1 风险。仅 `toggle_index`/`set_index`/`batch` 路径使用自愈任务（commit 后 spawn）。

### 3.4 新增 API 端点

#### 3.4.1 单条切换索引状态

**文件**：`app/routers/note_router.py`

> **⚠️ S1 修复**：向量同步 spawn 移到 `commit()` 成功**之后**，确保 MySQL 状态已持久化才触发后台任务。

```python
@router.post("/note/{note_id}/toggle-index", summary="切换知识库导入状态")
async def toggle_note_index(
    note_id: str,
    user_id: str = Depends(get_current_user_id),
    db: AsyncSession = Depends(get_db),
):
    """
    切换笔记的向量库导入状态（is_indexed）

    - True → False：从 ChromaDB 移除向量，不再参与 RAG 检索
    - False → True：异步写入 ChromaDB，恢复 RAG 检索可见性
    """
    note = await _get_note_service().toggle_index(db, note_id, user_id)
    await db.commit()  # ← 先 commit 持久化

    # ★ commit 成功后才 spawn 后台向量任务（S1 修复）
    # 任务内重读 DB 状态（自愈模式），即使 commit 与 spawn 之间出现异常也不影响
    if _get_note_service().vector_store:
        spawn_background_task(
            _get_note_service().sync_note_index_state(note.id),
            name="note_toggle_sync_state"
        )

    return success_response(data=NoteResponse.model_validate(note).model_dump())
```

#### 3.4.2 `note_service.py` 新增方法

**`toggle_index`**（仅翻转 MySQL 状态，不 spawn 向量任务）：

```python
async def toggle_index(self, db: AsyncSession, note_id: str, user_id: str) -> Note:
    """
    切换笔记的向量库导入状态（仅 MySQL 层，向量同步由调用方在 commit 后触发）

    ⚠️ S2 修复：前端改为传目标状态（set 语义），消除翻转竞态。
    但 toggle 端点仍保留翻转语义（单条快速切换），并发安全由自愈任务保证。
    """
    note = await self.get_note(db, note_id, user_id)

    # 翻转状态
    note.is_indexed = not note.is_indexed
    note.updated_at = func.now()
    await db.flush()
    await db.refresh(note)

    # ★ 不在此处 spawn 向量任务（S1 修复：由 router 层 commit 后 spawn）
    status = "加入" if note.is_indexed else "移出"
    logger.info(f"笔记{status}知识库: note_id={note_id}")
    return note
```

**`sync_note_index_state`**（公开方法——自愈任务入口，执行时重读 DB 状态，免疫乱序）：

> **⚠️ R2 修复**：v1.1 伪代码用 `get_note(db, note_id, user_id="*")` 必然 404，被 except 吞掉后自愈任务形同虚设。改为直接 SQL 查询，并暴露为公开方法（router 层可直接调用）。

```python
async def sync_note_index_state(self, note_id: str) -> None:
    """
    自愈式向量同步任务（S2 修复核心，公开方法）

    执行时从 MySQL 重读 is_indexed + 完整笔记内容，按实际值同步 ChromaDB：
    - True  → upsert 向量
    - False → 移除向量

    即使多个任务乱序执行，每个任务都以 DB 为准收敛，最终状态一致。
    使用独立 db session（与请求 session 解耦，commit 后仍可执行）。
    """
    from app.db.database import async_session_factory
    from sqlalchemy import select, text
    from app.models.note import Note

    try:
        async with async_session_factory() as db:
            # ★ 直接 SQL 查询（不走 get_note 的 user_id 校验）
            result = await db.execute(
                select(Note).where(Note.id == note_id)
            )
            note = result.scalar_one_or_none()

        if note is None:
            logger.warning(f"自愈任务：笔记不存在 note_id={note_id}")
            return

        if not self.vector_store:
            return

        if note.is_indexed:
            await self._sync_to_vector(note)
        else:
            await self._remove_from_vector(note.id)

        logger.debug(f"自愈向量同步完成: note_id={note_id}, is_indexed={note.is_indexed}")
    except Exception as e:
        logger.warning(f"自愈向量同步失败（不阻塞）: note_id={note_id}, error={e}")
```

**文件**：`app/services/note_service.py` — 新增 `set_index` 方法

> **⚠️ I4 修复**：批量操作不逐条 spawn 任务（避免 200 个并发 embedding 调用触发 DashScope 限流），改为**聚合处理**：
> - `unindex`：收集所有 note_id，一次批量删除（`vector_store` 新增按 note_ids 列表批删）
> - `index`：收集所有需写入的笔记，复用 `upsert_document` 的批量能力（20 条/批，与 `_generate_embeddings` 分批上限一致）

```python
async def set_index(
    self, db: AsyncSession, note_id: str, user_id: str, is_indexed: bool
) -> Note:
    """设置笔记的向量库导入状态（批量操作用，幂等）
    
    注意：本方法仅更新 MySQL 状态，不直接触发向量操作。
    批量向量同步由 batch_index_vectors 统一处理（I4 聚合）。
    """
    note = await self.get_note(db, note_id, user_id)
    if note.is_indexed == is_indexed:
        return note  # 已是目标状态，跳过

    note.is_indexed = is_indexed
    note.updated_at = func.now()
    await db.flush()
    await db.refresh(note)
    return note
```

**文件**：`app/services/note_service.py` — 新增 `batch_sync_vectors` 方法

> **⚠️ R3 修复**：v1.1 代码实为逐条循环，与「批量」承诺不符。修正为真正的批量操作。

```python
async def batch_sync_vectors(self, note_ids: List[str], user_id: str) -> None:
    """
    批量同步向量状态（I4 聚合 + R3 修正，在 router commit 后调用）

    从 MySQL 读取各笔记最新 is_indexed + 内容，分组处理：
    - is_indexed=False → ChromaDB 批量删除（where note_id $in [...]，一次调用）
    - is_indexed=True  → 批量 upsert（documents 列表按 20 条/批，复用 _generate_embeddings 分批能力）
    """
    if not self.vector_store:
        return

    from app.db.database import async_session_factory
    async with async_session_factory() as db:
        notes = await self.get_notes_by_ids(db, note_ids, user_id)

    to_upsert = [n for n in notes if n.is_indexed]
    to_delete_ids = [n.id for n in notes if not n.is_indexed]

    # ★ 批量删除（ChromaDB where 支持 $in，一次调用）
    if to_delete_ids:
        try:
            results = self.vector_store._notes_collection.get(
                where={"note_id": {"$in": to_delete_ids}}, include=[]
            )
            if results and results["ids"]:
                self.vector_store._notes_collection.delete(ids=results["ids"])
                logger.info(f"批量向量删除完成: {len(results['ids'])} 条")
        except Exception as e:
            logger.error(f"批量向量删除失败: {e}")

    # ★ 批量写入（按 20 条/批聚合，复用 _generate_embeddings 的批量能力）
    BATCH_SIZE = self.vector_store.EMBEDDING_BATCH_SIZE  # 20
    for i in range(0, len(to_upsert), BATCH_SIZE):
        batch = to_upsert[i:i + BATCH_SIZE]
        try:
            await self.vector_store.upsert_document(
                documents=[n.content or n.title for n in batch],
                metadatas=[{
                    "user_id": n.user_id, "note_id": n.id,
                    "title": n.title, "category": n.category or "",
                } for n in batch],
                ids=[f"note_{n.id}" for n in batch],
                collection="notes",
            )
            logger.debug(f"批量向量写入: {len(batch)} 条 (batch {i // BATCH_SIZE + 1})")
        except Exception as e:
            logger.error(f"批量向量写入失败: batch {i // BATCH_SIZE + 1}, error={e}")
```

## 4. 对 RAG 检索的影响

### 4.1 取消同步的笔记如何从向量库移除

**流程**：

```
用户点击「移出知识库」
    │
    ├─ ① MySQL: UPDATE is_indexed = FALSE（同步，主流程）
    │
    └─ ② ChromaDB: delete_note_vectors(note_id)（异步后台）
           │
           └─ notes_collection.delete(ids=[...])
              where={"note_id": note_id}
```

**时序保证**：
- MySQL 状态变更是同步的（请求返回前已落库）
- ChromaDB 删除是异步的（通常 < 1s 完成）
- 在异步删除完成前的极短窗口内，`search_notes` 仍可能返回该笔记 → **可接受**（RAG 本身是尽力而为，且 `semantic_search` 有 MySQL 回填校验 `deleted_at.is_(None)`）

### 4.2 对 Agent 对话中知识库检索的影响

| 场景 | 影响 |
|------|------|
| 笔记移出知识库后 | `vector_store.search_notes()` 不再返回该笔记（ChromaDB 中已删除） |
| `search_notes_tool` | 同上，Agent 无法通过语义搜索找到该笔记 |
| `keyword_search`（前端搜索框） | **不受影响** — 走 MySQL FULLTEXT/LIKE，不依赖 ChromaDB |
| `get_note_content_tool` | **不受影响** — 按 note_id 直接查 MySQL |
| `get_related_notes_tool` | 受影响 — 若底层用 `semantic_search`，则不再返回已移出的笔记 |

### 4.3 防御性过滤（可选增强）

虽然非 `is_indexed` 笔记不会写入 ChromaDB，理论上不会被检索到，但可在 `search_notes` 中增加双重保险：

```python
# vector_store.py search_notes 方法中，增加 metadata 过滤：
results = self._notes_collection.query(
    query_embeddings=query_embedding,
    n_results=top_k,
    where={
        "user_id": user_id,
        # 可选：如果存量数据有脏向量（改造前遗留），额外过滤
        # "is_indexed": True,  # 需要 _sync_to_vector 时写入该 metadata
    },
    include=["documents", "metadatas", "distances"],
)
```

> **v1 不实施**：因为 `is_indexed=False` 的笔记根本不会写入 ChromaDB，不存在脏数据问题。仅当后续引入「全局默认设置」或批量导入脚本时才考虑。

## 5. 边界情况

### 5.1 笔记更新时的同步策略

| 场景 | `is_indexed=True` | `is_indexed=False` |
|------|-------------------|-------------------|
| 更新内容 | 同步更新 ChromaDB 向量 | 不操作 ChromaDB |
| 更新标题/分类/标签 | 同步更新 ChromaDB 元数据 | 不操作 ChromaDB |
| 仅更新 `is_indexed` | 由 `toggle_index` 处理 | 由 `toggle_index` 处理 |

**关键保证**：`update_note` 采用条件式 spawn（§3.3.2）—— `is_indexed=True` 时 upsert 向量，`is_indexed=False` 时主动移除（处理从「已索引」改为「未索引」后、又更新内容的场景）。传内存对象（携带最新内容），无重读竞态。

### 5.2 笔记删除时的同步策略

| 场景 | 行为 | 说明 |
|------|------|------|
| 软删除（`delete_note`） | `delete_note_vectors(note_id)` | 无论 `is_indexed` 状态，ChromaDB delete 是幂等的 |
| 恢复（`restore_note`） | 仅 `is_indexed=True` 时重建向量 | **改造点**：恢复时尊重用户之前的选择 |
| 彻底删除（`permanent_delete`） | `delete_note_vectors(note_id)` | 同软删除，幂等 |
| 过期清理（`cleanup_expired_notes`） | `delete_note_vectors(note.id)` | 同上 |

### 5.3 批量操作处理

| 批量操作 | 向量影响 |
|---------|---------|
| `delete` | 移除向量（现有逻辑，不变） |
| `pin` / `unpin` | **不触发**向量同步。批量 pin/unpin 走 `pin_note`/`unpin_note`（`note_service.py:494-532`），这两个方法**不**调用 `_sync_to_vector`。注意：前端单个置顶（`NoteList.tsx:237` 走 `notesApi.update`）会触发 `update_note` → `_sync_to_vector`，这是**已有行为**，本次不修 |
| `move` | **不触发**向量同步（`move_note_by_id` 不调 `_sync_to_vector`）。但 ChromaDB 中已存在的向量 metadata `category` 字段会过期——这是**预存在问题**（改造前即存在），本次不修 |
| `restore` | 仅 `is_indexed=True` 时重建（改造点） |
| `permanent_delete` | 移除向量（现有逻辑，不变） |
| `index` | **新增**：批量加入知识库 |
| `unindex` | **新增**：批量移出知识库 |

**批量操作安全限制**：与现有 `permanent_delete`（≤50）/ `restore`（≤100）一致，`index`/`unindex` 上限 200 条/次（已写入 `BatchOperation.validate_operation_limits`，见 §3.4.3 Schema 校验）。

### 5.4 回收站恢复的特殊处理

**场景**：用户在 `is_indexed=True` 时删除笔记 → 在回收站中手动将 `is_indexed` 改为 `False`（暂不支持，回收站 UI 无此入口）→ 恢复。

**当前设计**：回收站中不提供修改 `is_indexed` 的入口（v1 不做）。恢复时直接读取笔记的 `is_indexed` 字段决定行为。

> **⚠️ I3 补充**：回收站内笔记调用 `toggle-index` 会因 `get_note` 过滤 `deleted_at IS NULL`（`note_service.py:130`）返回 404——行为正确但属隐式设计，**明确记录**：回收站内笔记不可切换索引状态。

### 5.5 并发安全

> **⚠️ S2 修复**：原方案论证「后台任务按提交顺序排队」不成立——`spawn_background_task` 基于 `asyncio.create_task`，任务是并发执行、无排队保证。此外 `toggle_index` 的读-改-写（`not note.is_indexed`）非原子，并发请求存在 lost update。

**场景**：用户快速连续点击「加入知识库」→「移出知识库」→「加入知识库」。

**修复方案（双层防护）**：

1. **MySQL 层**：`toggle_index` 使用 `SELECT ... FOR UPDATE` 行锁保护读-改-写原子性（或在应用层用 Redis 分布式锁，与现有 `rate_limit` 模式一致）
2. **ChromaDB 层**：所有向量同步任务统一采用 `sync_note_index_state` **自愈模式**——任务执行时从 MySQL 重读 `is_indexed` 最新状态，按实际值同步 ChromaDB。即使多个任务乱序执行，每个任务都以 DB 为准收敛，最终状态一致

```python
# 自愈任务执行流程：
# 1. 从 MySQL 读取 note.is_indexed（最新值）
# 2. if is_indexed → upsert 向量
#    else → 移除向量
# 无论任务以何种顺序执行，最终 ChromaDB 状态与 DB 一致
```

**前端配合**：卡片/编辑器点击时加 loading 状态禁用重复点击（防抖 300ms），从源头减少并发。

### 5.6 AI 工具创建/更新笔记

- **创建**：`create_note_tool` 不传 `is_indexed` → Schema 默认 `True` → **行为与改造前一致**（AI 创建的笔记默认加入知识库）
- **更新**：`update_note_tool` 调用 `note_service.update_note` → 走条件式 spawn（§3.3.2）。未索引笔记被 AI 更新内容时，走 `else` 分支主动移除向量（或跳过，幂等）
